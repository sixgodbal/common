## 1. 工具定位

在指定文件夹里搜索**文件内部的文字**，找出文字出现在哪个文件、哪一行。

和 Everything 的区别：

- Everything：搜文件名
- 文本快搜：搜文件内容

设计约束：

- 点击“开始查找”才扫描，**不建常驻索引**
- 纯 Python 标准库（tkinter），不联网、不写注册表
- 多文件夹、多线程、可停止
- 优先速度：先字节级预筛，命中后才解码、算行号

## 2. 当前功能清单

### 2.1 搜索范围

- 添加 / 移除多个文件夹
- 可递归子目录
- 可跳过隐藏 / 系统文件（默认开启）
- 默认排除：`.git`、`node_modules`、`__pycache__`、`.venv`、`venv`、`env`、`dist`、`build`、`target`、`out`、`.idea`、`.vs`
- 始终跳过：`$RECYCLE.BIN`、`System Volume Information`
- 支持环境变量路径，如 `%USERPROFILE%\Documents`
- 支持相对本程序目录的相对路径
- 自动去重；如果同时添加父目录和子目录，只搜父目录

### 2.2 搜索方式

- 按完整文字做子串匹配
- 可区分 / 不区分大小写（默认不区分；主要影响 ASCII 字母）
- 按扩展名过滤；留空 = 所有文件（自动跳过二进制）
- 最大文件大小限制（默认 20 MB）
- 结果上限（默认 3000 个命中文件）
- 每个文件最多统计 5000 处匹配，最多展示 80 条预览片段
- 按钮触发；支持 `Enter` / `F5`；可随时停止

### 2.3 支持的文件

纯文本 / 代码：

`txt, md, markdown, log, csv, tsv, json, jsonl, xml, html, htm, css, js, jsx, ts, tsx, py, java, c, cc, cpp, cxx, h, hpp, cs, go, rs, php, rb, sql, sh, bat, cmd, ps1, yml, yaml, ini, cfg, conf, toml, properties, env, tex, rst, adoc, eml, srt, vtt`

Office / 电子书：

- `docx, docm`：读取 `word/document.xml`、页眉页脚、脚注尾注
- `xlsx, xlsm`：读取 `xl/sharedStrings.xml` 和各 sheet XML
- `pptx, pptm`：读取 `ppt/slides/*.xml`、`ppt/notesSlides/*.xml`
- `epub`：读取 `.xhtml/.html/.htm`
- `odt, ods, odp`：读取 `content.xml`

不支持：

- PDF
- 旧版 `doc / xls / ppt` 二进制格式
- zip / rar / 7z 压缩包内部文件

### 2.4 结果与操作

- 结果列表：文件名、匹配数、首个位置（行:列）、大小、修改时间、所在文件夹
- 点表头排序：文件名、匹配数、首个位置、大小、修改时间、文件夹
- 默认按完整路径（文件夹列）排序
- 选中结果后在右下角预览所有匹配行（最多 80 条），高亮关键词
- 双击结果：系统默认程序打开文件
- 右键结果：打开文件 / 在资源管理器中显示 / 复制路径 / 复制匹配内容
- 如果 PATH 里有 `code`（VS Code），右键可跳到对应行
- 导出 CSV（UTF-8 BOM，Excel 可直接打开）
- 状态栏显示扫描进度、命中数、耗时、MB/s

- 用 `entry.stat(follow_symlinks=False)` 一次拿 size/mtime/attributes

### 5.4 编码 / 文本搜索核心

| 函数 | 当前行号 | 作用 |
| --- | --- | --- |
| `_detect_unicode_encoding(data, sample)` | 443 | 识别 UTF-8 BOM、UTF-16/32 BOM、无 BOM UTF-16 LE/BE |
| `_looks_binary(data)` | 461 | NUL 或控制字符比例判断二进制 |
| `_text_sanity(text)` | 471 | 解码后前 4096 字符的可打印性检查 |
| `find_positions(hay, needle, cap, stop_event)` | 479 | 不重叠查找，最多 `cap` 个，返回是否还有更多 |
| `_snippet(...)` | 498 | 从匹配行截取上下文；长行按匹配位置开窗 |
| `hit_from_text(...)` | 510 | 核心：统计位置、计算行/列、生成最多 80 条片段，返回结果 dict |
| `search_text_file(...)` | 549 | 读文件 → 编码/二进制判断 → 字节预筛 → 解码确认 → 结果 |

`search_text_file` 的顺序（不要随便改）：

1. `f.read()` 读整个文件（见“性能陷阱”）
2. 如果长度超过 `max_bytes`，跳过
3. BOM / 无 BOM UTF-16 检测：能识别就直接解码成 `str`，走 `hit_from_text`
4. 否则 `_looks_binary`：NUL 或控制字符太多就跳过
5. 生成候选编码：`utf-8`、`gb18030`（ASCII 查询两者 pattern 相同，但仍保留两个解码回退）
6. 用 bytes 的 `find` 做预筛；不区分大小写且查询是 ASCII 时用 `data.lower()`
7. 只有预筛命中才 `data.decode(encoding)`，再做 `_text_sanity` 和 `hit_from_text`
8. `hit_from_text` 找不到（例如字节巧合）就尝试下一个编码

返回结构（结果 dict）：

```python
{
    "path": 完整路径,
    "name": 文件名,
    "folder": 所在文件夹,
    "size": 字节数,
    "mtime": 修改时间戳,
    "count": 匹配处数（最多 5000）,
    "truncated": 是否超过 5000,
    "snippets": [(行号, 列号, 片段), ...],  # 最多 80
    "source": "text" | "office",
}
```

线程模型：

- 一个后台线程跑 `_search_worker`，负责枚举和提交任务
- `ThreadPoolExecutor` 默认 `min(32, max(4, cpu*2))` 个线程
- 最多同时挂起 `workers*3` 个 future，避免一次提交几十万个任务
- worker 不碰 Tk，只往 `queue.Queue` 放事件
- 主线程每 60ms 最多处理 300 个事件
- 达到 `max_results` 后，worker 不再把 `hit` 事件放进队列，但 `hits/matches` 仍继续统计
  （否则一次搜索几十万条会把 UI 队列拖死）

停止逻辑：

- `stop_search()` 设置 `threading.Event`
- 枚举、单文件搜索、查找循环都会检查
- worker 退出后发 `done`，payload 带 `stopped=True`
- `executor.shutdown(wait=False, cancel_futures=True)`；Python 3.8 用 `except TypeError` 回退

## 7. 性能设计与实测

### 7.1 关键优化

1. **不建索引**：每次只读候选文件；小范围搜索启动快。
2. **先字节、后解码**：未命中的文件不解码、不算行号。
3. **C 层操作**：`bytes.find`、`bytes.lower`、`translate`、`count`；避免 Python 循环扫字节。
4. **只对命中文件做重活**：`hit_from_text` 才建行号表、生成片段。
5. **线程池**：I/O 并行；GIL 对短小的 `find` 影响有限。
6. **结果限流**：worker 只发前 `max_results` 条 `hit` 事件，避免队列爆炸。
7. **批量 UI 更新**：60ms 一次，最多 300 个事件，避免每命中一次就 `after`。

### 7.2 本机基准（2026-10-26）

测试集：2000 个 txt，共 22.16 MB，2000 个文件分布在不同子目录。

| 场景 | 线程 | 时间 | 吞吐 |
| --- | --- | --- | --- |
| 有 40 个命中 | 1 | 0.14-0.17s | ~130-155 MB/s |
| 有 40 个命中 | 8 | 0.097s | ~228 MB/s |
| 无命中 | 16-24 | 0.097-0.102s | ~217-228 MB/s |
| 2000 个文件全部命中、35 万处匹配 | 自动 | 0.74s | — |

结论：小文件场景主要受文件系统和杀毒软件影响；纯 CPU 的 `find` 不是瓶颈。
真实目录（尤其机械盘、网络盘、开了实时扫描的杀毒软件）会明显慢一些。

### 7.3 性能陷阱（回归检查清单）

改代码时重点检查这些：

- **不要**把 `f.read()` 改成 `f.read(max_bytes + 1)`
  - 之前这样写，每个 11KB 文件都会申请 20MB 缓冲，2000 个文件从 0.1s 变成 5.8s
  - 现在按文件实际大小读；`max_bytes` 在枚举阶段已经过滤
- **不要**用 Python `for` 循环逐字节检查 8KB 样本
  - `_looks_binary` 用 256 字节翻译表 + `count`
  - `_text_sanity` 用 `str.translate` 删除坏字符后算长度差
- **不要**对未命中文件先 `decode`
  - 先 bytes `find`，命中才解码
- **不要**让 worker 把全部命中都塞进队列
  - 只发前 `max_results` 条；统计用 `hits/matches`
- **不要**在每个命中回调里直接操作 Tk
  - 统一走 queue + `_pump`
- **不要**在测试时显示主窗口
  - 用户明确要求测试不要抢焦点；用隐藏 App 模式（见第 9 节）

## 8. 已知限制

- 不支持 PDF、旧版 `doc/xls/ppt`
- 不支持压缩包内部文件
- 不支持正则、通配符、整词匹配、多关键词 AND/OR（当前是字面量子串）
- 非 ASCII 的大小写不敏感匹配不完整；中文无大小写，通常不受影响
- 超大文件默认跳过（可调大 `max_size_mb`，但会占内存）
- Office 文档行号是提取文本的行号
- 结果上限只影响显示/导出，统计仍准确
- `always_on_top` 没有 UI 开关，只能改配置

## 10. 后续扩展建议

### 10.1 加 PDF

需要引入第三方解析（`pypdf`、`pdfminer.six`、`PyMuPDF`）或外部 `pdftotext`。
建议做法：

1. 在 `OFFICE_EXTS` 加 `.pdf`
2. 新增 `extract_pdf_text(path)`，返回 `str`
3. 在 `extract_office_text` 或 `search_one` 里路由
4. 更新 `README.md` 的支持格式和限制
5. 补充回归用例（扫描版 PDF 需要 OCR，另说）

### 10.2 加正则 / 整词 / 多关键词

- 在 `_collect_options` 增加选项
- `hit_from_text` 里把 `str.find` 换成 `re.finditer`
- 注意：正则可能回溯爆炸，需要超时/长度限制
- 多关键词 AND/OR 可以先分别找，再合并文件集合

### 10.3 加索引

当前架构是“每次扫描”。如果以后要常驻索引：

- 需要独立的索引存储（SQLite / Lucene / 自建倒排）
- 需要文件变更监听或定期增量更新
- UI、搜索、进度模型都要改
- 不建议在这个单文件里硬塞；可以先拆 `search_core.py`

### 10.4 加新格式

纯文本类：直接加扩展名即可。
压缩容器类（docx/xlsx/pptx/epub/odf）：在 `extract_office_text` 里加 `kind` 和 `targets`，在 `_xml_to_text` 里加去标签规则。
